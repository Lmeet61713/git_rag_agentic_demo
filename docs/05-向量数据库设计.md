# 向量数据库设计

## 1. 设计原则

不要建立物理层级的双向量数据库。

采用：

```text
一个 Chroma 持久化目录
+ 逻辑层级 metadata
+ 两阶段检索
```

原因是：

- 10 个项目规模不大。
- 单一 collection 更容易维护。
- metadata 过滤比多库维护简单。
- 多项目检索时不需要遍历多个库。
- 以后项目变多时可以再拆。

## 2. 逻辑层级

第一层：项目。

```text
project_id
owner
repo
```

第二层：文件。

```text
path
file_type
language
commit_sha
file_hash
```

第三层：内容块。

```text
chunk_index
text
vector
```

## 4. Collection 规划

第一版建议使用一个主 collection：

```text
collection: myagentic
```

通过 metadata 区分：

- project_id
- file_type
- language
- path

如果以后出现以下情况，再拆 collection：

- 项目数量大幅增长。
- 单个项目向量数量过大。
- 需要按项目做独立删除和隔离。
- 图片描述索引需要单独管理。

## 5. 项目级召回

可以为每个项目生成一个项目摘要向量：

```text
README 摘要
项目文件树
主要语言
项目简介
```

项目摘要也写入向量库：

```json
{
  "file_type": "project_summary",
  "project_id": "owner/repo-main",
  "text": "这是一个 FastAPI 后端项目..."
}
```

检索时：

```text
“这个项目大致有什么”
→ 直接读取项目元数据 + README
→ 不一定需要向量检索
```

## 6. Embedding 设计

没有专用代码向量模型，所以采用：

```text
通用文本 embedding + 代码上下文
```

代码块在向量化前拼入：

```text
文件路径
编程语言
函数或类名
关键注释
代码内容
```

示例：

```text
path: src/auth.py
language: python
symbol: login
async def login(username, password): ...
```

检索时不能只靠向量：

```text
向量检索
+ 关键词检索
+ 路径匹配
+ 文件树检索
```

## 7. 图片检索设计

图片不直接向量化图片像素。

流程：

```text
图片原文件
→ 阿里云图生文 API
→ 图片描述文本
→ 文本 embedding
→ 图片路径和描述写入 Chroma
```

图片记录本质上就是：

```text
键：图片描述向量
值：图片路径和元数据
```

额外保留路径关键词：

- 文件名
- 目录名
- 扩展名

用于搜索 logo、screenshot、banner 这类明确资源。

## 8. 两阶段检索

第一阶段：确定相关项目。

```text
查询
→ 项目摘要/项目元数据
→ 找到 top 项目
```

第二阶段：确定相关文件。

```text
相关项目
→ 代码/文档/图片向量检索
→ 按 file_type 过滤
→ 找到 top 文件块
```

第三阶段：Agent 读取原文。

```text
文件块
→ Agent 读取文件内容
→ 确认是否真正相关
→ 汇总回答
```

## 9. 增量更新

首次入库：

```text
clone 仓库
全量解析
全量向量化
保存 commit_sha
保存 file_hash
```

后续更新：

```text
拉取最新代码
对比 commit_sha
找出变化文件
只重新处理变化文件
删除旧文件对应向量
写入新向量
更新索引状态
```

需要维护：

```text
project_id
path
file_hash
commit_sha
chunk_index
```

## 10. 异步任务

第一版使用 FastAPI 后台任务。

每个仓库入库任务应有状态：

```text
pending
running
success
failed
```

任务阶段：

```text
cloning
scanning
parsing
embedding
writing
```
